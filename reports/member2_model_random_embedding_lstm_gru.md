## 4.1 模型定位与研究问题

本项目把 Yelp 评论情感判定为负向（0）或正向（1）的二分类问题。按题目要求，第 3 项最低要求必须**同时包含并比较**两种 embedding 策略；本组的分工是：

| 组别 | 负责人 | Embedding | 本文章节 |
|---|---|---|---|
| 基础模型 | 成员二 | **随机初始化、随模型训练** | 本章（4.1–4.9） |
| 对照实验 | 成员三 | GloVe / Word2Vec 预训练 | 报告 Experiments 部分 |
| 进阶模型 | 成员四 | BERT 预训练语言模型 | 报告 Advanced Model 部分 |

因此本章要回答三个问题：

1. 在成员一固定的全量清洗划分上，随机初始化 Embedding 的双向循环网络能达到什么验证性能？
2. 在数据、词表、截断长度、优化器与训练预算**完全一致**的前提下，**LSTM 与 GRU** 的差别有多大？
3. 该模型的训练成本（每轮耗时、总时长、峰值显存、参数量）是多少？这组数字是成员四与 BERT 做性价比对比的基线。

> 说明：随机初始化的词向量不含外部语言知识，全部情感判别能力都必须从 503,979 条标注评论中学到；
> 这也正是它与成员三预训练词向量对照组的**唯一**区别所在。

### 4.2.2 文本表示

| 环节 | 采用方案 | 理由 |
|---|---|---|
| 小写化 | `text.lower()` | 与成员一参考实现一致，降低词表稀疏性 |
| 分词 | 正则 `\w+\|[^\w\s]`（词 / 单个标点） | 与成员一 `scripts/train_lstm.py:17` **逐字一致**，保证与历史实验可比；保留否定词、标点与数字（`not good`、`!!!`、`1 star` 都带情感信息） |
| 词表 | **仅由训练集**拟合，30,000 个 id 含 `<pad>`/`<unk>` | 验证/测试集不参与拟合，避免泄漏；30,000 实测覆盖训练集 99.32% 的 token |
| 特殊符 | `<pad>` = 0，`<unk>` = 1 | `<pad>` 不参与梯度，配合 `padding_idx=0` |
| 词表排序 | 按 (−频次, 字典序) 分配 id | **确定性**：同频词顺序不依赖插入顺序，跨机器可复现（成员一的 `Counter.most_common` 不具备该性质） |
| 未登录词 | 训练集外 token → `<unk>`(1) | 实测验证集 token OOV 率 **0.69%** |
| 变长处理 | batch 内**动态 padding**（`pad_sequence`）+ `pack_padded_sequence` | 平均有效长度 135.2，远小于固定 256，可省下大量无效计算；pack 还能避免 PAD 污染末状态 |
| 截断长度 | `max_len = 256` | 见下表 |

**截断长度的取舍依据（实测）：**

| `max_len` | 被截断文档比例 | 保留 token 比例 | 平均有效长度 | 相对计算量 |
|---:|---:|---:|---:|---:|
| 128 | 46.96% | 57.66% | 95.7 | 0.5× |
| **256（采用）** | **18.98%** | **81.45%** | **135.2** | **1×** |
| 384 | 8.21% | 91.33% | 151.6 | 1.5× |
| 512 | 3.83% | 95.75% | 159.0 | 2× |
| 768 | 0.99% | 98.93% | 164.2 | 3× |

取 256 的理由：评论 token 长度中位数 120、P95 为 467；把长度降到 128 会丢掉 42% 的 token，而升到 512 会把循环层的计算量翻倍却只多保留 14% 的 token。256 同时与仓库历史运行的取值一致，便于横向对照。**代价是约 19% 的评论尾部被截断**，这一点在第 4.8 节列为已知局限。

## 4.3 模型结构

### 4.3.1 形式化描述

设一条评论被编码为词 id 序列 $x_{1:T}$，$E\in\mathbb{R}^{30000\times100}$ 为随机初始化的词向量矩阵：

$$
\begin{aligned}
\mathbf{e}_t &= \mathrm{Dropout}_{0.1}\big(E[x_t]\big), \qquad E \sim \mathcal{U}(-0.1, 0.1),\ \text{可训练}\\
\overrightarrow{\mathbf{h}}_t &= \mathrm{LSTM}\big(\mathbf{e}_t,\ \overrightarrow{\mathbf{h}}_{t-1}\big), \qquad
\overleftarrow{\mathbf{h}}_t = \mathrm{LSTM}\big(\mathbf{e}_t,\ \overleftarrow{\mathbf{h}}_{t+1}\big)\\
\mathbf{z} &= \big[\overrightarrow{\mathbf{h}}_{T}\ ;\ \overleftarrow{\mathbf{h}}_{1}\big] \in \mathbb{R}^{256} \\
\hat{\mathbf{y}} &= \mathrm{softmax}\big(W\,\mathrm{Dropout}_{0.3}(\mathbf{z}) + \mathbf{b}\big), \qquad W\in\mathbb{R}^{2\times256}
\end{aligned}
$$

换用 GRU 时只把 $\mathrm{LSTM}$ 替换为 $\mathrm{GRU}$，其余结构、初始化与超参数完全不变，因此二者的差异可以归因于**循环单元本身**。

### 4.3.2 层表与参数量

| 层 | 配置 | 输出维度 | 参数量 |
|---|---|---:|---:|
| Embedding | `vocab=30,000`，`dim=100`，`padding_idx=0`，随机均匀初始化 | 100 | 3,000,000 |
| Embedding Dropout | $p=0.1$ | 100 | 0 |
| BiLSTM / BiGRU | `hidden=128`/方向，1 层，`batch_first`，`pack_padded_sequence` | 256 | 235,520 / 176,640 |
| Dropout | $p=0.3$ | 256 | 0 |
| Linear | $256\to2$ | 2 | 514 |
| **合计** | | | **3,236,034（BiLSTM）/ 3,177,154（BiGRU）** |

### 4.3.3 三个实现细节及其作用

1. **`pack_padded_sequence`（输入真实长度）**
   若只做 padding 而不 pack，循环层会把 PAD 当成正常 token 继续推进隐状态；此时再用"最后一个时间步"当句向量，取到的其实是 pad 位置的输出，句向量会随 batch 内最长序列长度而变化。pack 之后，每个样本只在自身的真实长度内运算，既正确又省算力。

2. **`padding_idx=0` 且该行恒为 0**
   保证 PAD 的 embedding 不参与梯度更新，不会把"填充"学成一个有意义的词。

3. **随机初始化用 $\mathcal{U}(-0.1,0.1)$ 而非 PyTorch 默认的 $\mathcal{N}(0,1)$**
   默认正态初值会让 100 维点积的方差过大，LSTM 的门控一开始就接近饱和，前几轮 loss 抖动明显、收敛更慢。

此外，模型把 embedding 层设计成**可注入预训练矩阵**的接口（`embedding_weights` 参数），成员三只需传入按同一份词表对齐的 GloVe 矩阵即可得到"预训练 embedding"版本，循环层与分类头保持不变——这是本章与成员三实验能够公平对比的工程保障。

## 4.4 训练设置

| 项目 | 取值 | 说明 |
|---|---|---|
| 优化器 | AdamW | $\beta$ 用默认值 |
| 学习率 | $1\times10^{-3}$ | 与仓库历史运行一致 |
| 权重衰减 | $1\times10^{-2}$ | 显式写出并记录，不依赖库默认值 |
| Batch size | 128 | — |
| 梯度裁剪 | $\|\mathbf{g}\|_2 \le 1.0$ | 循环网络训练不稳定的常规兜底 |
| Dropout | 0.3（循环输出）+ 0.1（embedding） | 历史曲线显示训练准确率接近 100% 而验证约 89%，存在明显过拟合，故加 embedding dropout |

| 选模指标 | **验证集 Macro-F1** | 只看验证集；测试集全程不参与选模 |
| 混合精度 | AMP（仅 CUDA 可用时启用） | 验证与最终评估固定用 FP32，避免数值噪声影响指标 |
| 随机种子 | 42 | 与数据划分种子一致 |
| 硬件与软件 | NVIDIA GTX 1650 Max-Q（4 GB）/ PyTorch 2.6.0+cu124 / CUDA 12.4 / Python 3.12 | 记录在 `runs/<run>/config.json` 的 `environment` 字段 |

**防泄漏与可复现措施**

- 训练脚本启动时强制核对 `processed_data/*.csv` 的 SHA-256、行数、集合内重复与集合间重叠，任何一项不符直接报错退出；
- 词表只由训练集拟合，验证/测试集仅用于评估；
- 测试集评估默认关闭，需显式开启，且规定只在配置锁定后评估一次；
- 每轮把指标追加写入 `metrics.jsonl` 与 `training_log.csv`，中断不丢结果；`last_full.pt` 保存优化器状态以支持精确续训。

## 4.6 LSTM 与 GRU 的对比

| 对比项 | BiLSTM | BiGRU | 差异 |
|---|---:|---:|---:|
| 验证 Macro-F1 | 95.33% | 95.65% | +0.32 个百分点 |
| 验证 Accuracy | 95.33% | 95.65% | +0.32 个百分点 |
| 最佳轮次 | 3 | 2 | — |
| 参数量 | 3,236,034 | 3,177,154 | -1.8% |
| 每轮耗时 | 567 s | 422 s | 1.34× |
| 总训练时长 | 47.3 min | 35.2 min | — |

**解读**

1. **指标**：BiGRU 的验证 Macro-F1 比 BiLSTM 高 **0.32 个百分点**（95.33% → 95.65%）。两者在同一数据、同一词表、同一预算下训练，差别只能来自循环单元本身。
2. **参数与速度**：GRU 把 LSTM 的输入门/遗忘门/输出门简化为重置门与更新门，每方向参数少约 25%（3,236,034 → 3,177,154，含 embedding 后差 -1.8%），实测每轮耗时从 567 s 降到 422 s，相当于 **1.34 倍加速**（GRU 用时仅为 LSTM 的 74%）。由于本模型 92.7% 的参数集中在 embedding 上，参数量的差别被稀释，速度提升主要来自 GRU 更少的门控运算。
3. **收敛**：GRU 在第 1 轮就达到 95.29%，而 LSTM 第 1 轮为 94.55%；GRU 的最佳轮次出现在第 2 轮、LSTM 在第 3 轮，说明 GRU 收敛更快。
4. **结论口径**：本次只跑了单个种子，因此不应断言"GRU 一定优于 LSTM"；更严谨的表述是——**在本任务与本次预算下，GRU 以更少的参数和更短的训练时间取得了略高的验证 F1**。若要把差异写进结论，建议补跑种子 43/44 并报告均值±标准差。

| 参数量 | 3,236,034 | 3,177,154 | embedding 占 92.7% |

> 与 BERT 对比时必须说明三点：① 本模型**从头训练**（embedding 也是随机初始化），BERT 是预训练后微调，本章记录的是**任务训练**成本，不含预训练成本；② 本模型的 `max_len` 是**词**数，BERT 是**子词**数，序列长度不可直接等同；③ 本章的耗时来自 4 GB 笔记本 GPU，与成员四所用的服务器/Colab 硬件不同，跨机器只能比较**数量级**，不能比较绝对值。

## 4.8 局限

1. **单种子结果**：本章只跑了 seed = 42，未做多种子均值与标准差，因此 LSTM 与 GRU 的微小差距不足以支撑"某单元更优"的强结论。
2. **截断损失**：`max_len = 256` 会截断 18.98% 的评论、丢弃 18.55% 的 token；若情感线索主要出现在长评论尾部（例如先抑后扬的结尾），模型会系统性判错。
3. **随机 embedding 无外部知识**：全部语义信息只能来自 50 万条标注样本；对低频词与未登录词（验证集 token OOV 0.69%）尤其不利。
4. **长程依赖的天花板**：LSTM/GRU 通过固定维度的隐状态压缩整句，超长文本的信息瓶颈明显，这是成员四引入 BERT 的直接动机。
5. **成本比较条件**：耗时与显存依赖具体硬件与是否启用 AMP，跨机器不可直接比较；报告中必须写明设备与精度设置。
6. **本次是受限预算的本地复现**：受 4 GB 笔记本 GPU 限制只跑了 5 轮（`config.yaml` 的正式预算是 20 轮 + 早停），
   且只跑了一个种子；测试集尚未评估。因此本章结论应表述为"在本次预算下的对照结果"，
   正式提交前建议在 RTX 4080 上按 20 轮预算补跑，并补种子 43/44 报告均值±标准差。

## 附录 B　复现命令

```bash
git clone https://github.com/yancanbethebest/comp7015-yelp-sentiment.git
cd comp7015-yelp-sentiment
git lfs install && git lfs pull
python -m pip install -r requirements-training.txt

# 链路自检（1~2 分钟）
python -m models.lstm_gru_random.train --smoke-test

# 正式训练
python -m models.lstm_gru_random.train
python -m models.lstm_gru_random.train --rnn-type gru --run-name member2_bigru_random_full_seed42
```

单次运行的完整配置、环境快照与 git commit 记录在 `runs/<run_name>/config.json`，
指标汇总在 `metrics.json`，逐轮日志在 `history.json` 与 `training_log.csv`。
